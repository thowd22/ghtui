# macOS and Linux curl bootstrap release contract

Status: researched delivery contract, 2026-10-14. Requested by the user; implementation and native platform verification remain unstarted. TASK-68 owns the installer and release artifacts; TASK-69 owns near-end hosted CI/CD. No remote, release URL, domain, credentials, or publication is provisioned by this decision.

## Decision

Use one repository-owned, Bash 3.2-compatible `install.sh` as the primary distribution interface for both macOS and Linux. It selects a verified prebuilt executable; it does not build Rust on the user's machine. Publish versioned release archives, checksums and release metadata, not .dmg/.pkg/.deb/.rpm installers, package-manager repositories, a Homebrew tap, or a Windows installer. Those native packaging formats are outside the current delivery requirements.

The intended user experience is a single `curl ... | bash` command once the actual GitHub repository and public release assets exist. Also document download-inspect-run and manual verified archive installation. Do not put an invented or nonworking installation URL into the README. Prefer GitHub Releases initially; no separate website or custom domain is required.

The same script does not mean the same executable. Plan four release artifacts: `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-unknown-linux-musl`, and `aarch64-unknown-linux-musl`. Musl is the planned Linux portability strategy, not evidence that all Linux distributions work. Record actual supported minimum macOS/Linux and CPU/runtime baselines after executing native tests. Unsupported OS/architecture combinations fail clearly rather than downloading an approximately matching binary. Account for Apple Silicon/translated shells and validate the executable architecture. A missing Bash or curl is an explicit bootstrap prerequisite, not a reason to silently invoke a package manager.

## Research and tool choice

[Claude Code's official setup documentation](https://code.claude.com/docs/en/setup) demonstrates one native `curl ... | bash` entry point for macOS/Linux and a version argument. This supports the interface choice; its automatic updater, authentication, runtime requirements and Windows support are not adopted by ghtui.

[cargo-dist's shell installer](https://axodotdev.github.io/cargo-dist/book/installers/shell.html) is a viable Rust release-tool alternative: it detects platforms, downloads archives and installs binaries. Its [documented usage controls](https://axodotdev.github.io/cargo-dist/book/installers/usage.html) include custom install directories, no-PATH-modification and unmanaged modes. Its [checksum documentation](https://axodotdev.github.io/cargo-dist/book/artifacts/checksums.html) distinguishes generating checksum assets from verifying fetched artifacts; documentation and current implementation can differ. Do not infer integrity checks, archive safety or exact target behavior from the tool name. Pin and audit any release generator actually selected.

Recommendation for this project's small four-target surface: keep the entry point as a short, independently tested project-owned script. Avoid coupling installation semantics to an auto-updater or generated pipeline. cargo-dist remains an optional build-time implementation aid, not a new end-user dependency or a committed additional installer. Release automation must still satisfy the exact contract below if it uses a generator.

## Installation behavior and safety

- Detect supported OS and architecture, then resolve Latest once to an exact release version. All binary, manifest and checksum requests use that same version; never combine changing Latest asset URLs. Support an explicit version pin and a quoted absolute installation-directory override.
- Default to a per-user executable directory such as `$HOME/.local/bin`. Never request sudo or silently write system directories. Do not modify shell startup files by default; print shell-appropriate PATH guidance, detect a shadowing older binary, and explain that a child script cannot change its parent shell's PATH.
- Do not install gh/git, invoke gh login, read tokens, or change accounts. Check presence and report official dependency/setup guidance; missing gh or auth must not prevent genuinely independent local Git workflows. Bootstrap downloads public release assets without GitHub authentication. No Rust, Node, jq, or image helper is required on the user's machine.
- Use certificate-verified HTTPS with HTTPS-only redirects, meaningful HTTP error handling, bounded connection/transfer timeouts and a private temporary directory. Never use insecure TLS flags or print credential-bearing environment values. [curl's official options](https://curl.se/docs/manpage.html) describe protocol restriction and HTTP failure handling.
- Verify the selected artifact's SHA-256 against exact-version metadata before extraction or execution. Use platform-available SHA-256 tools. Reject absent, duplicate, malformed, wrong-version or wrong-target metadata and checksum mismatches. Preflight archive member names/types: refuse traversal, absolute paths, symlinks/hardlinks and unexpected executable payloads. Extract only into the private staging directory; install only the explicitly identified ghtui binary.
- Execute a bounded version/help validation only after integrity and target checks. Stage beside the final target and replace atomically on the same filesystem. Refuse unrelated or symlinked destination files rather than following or overwriting them. Track ownership using bounded installer metadata, with permissions/symlink checks; do not share that metadata with private application drafts. Interrupted download, extraction, validation or replacement leaves the previous usable executable intact. Define and test concurrency/receipt ordering.
- Put effectful logic inside a complete final entry point so common truncated streamed-script prefixes do not perform partial installs. Document the plain pipeline's upstream exit-status caveat and offer a checked download-then-run alternative. Streaming a script still trusts the script publisher; this is not a sandbox.
- Upgrade by explicitly rerunning the same installer. Version pinning permits an explicit rollback. Do not add background auto-update, an in-app updater, or an extra updater executable. Repeated installation of the same verified version is safe. Uninstall removes only verified installer-owned executable/metadata and preserves configuration, cached data, drafts and repositories; data removal is separate and explicit.
- Retain optional avatar/diff capability fallbacks, usernames and no-color readability. The installer does not add required services or change Git/GitHub semantics.

SHA-256 downloaded from the same publisher detects corruption but does not authenticate a compromised publisher or the bootstrap script. Publish build provenance and document optional independent verification through [GitHub artifact attestations and gh](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations), subject to actual repository/plan eligibility. Do not require bootstrap authentication or claim signing/notarization without real evidence. Signing/notarization credentials, if later needed, are a separately recorded delivery constraint, not authority to bypass host security.

## Parallel source implementation protocol (2026-10-15; unverified)

TASK-68 now has an authorised isolated SOURCE-ONLY implementation slice; its formal TASK-67/73 release dependencies and all acceptance/native gates remain open. No installer/release/test execution, hosted asset or working install URL is claimed by this section.

The installer requires an explicit public HTTPS `--release-base` until actual hosting exists. Latest downloads `latest/download/release-version.txt` once; every subsequent request uses `download/vX.Y.Z/`. Exact-version `ghtui-manifest-v1.txt` starts with `ghtui-release-v1 vX.Y.Z` and contains exactly four `artifact TARGET ARCHIVE ARCHIVE_SHA256 ARCHIVE_BYTES BINARY_SHA256 BINARY_BYTES` records. Separate `SHA256SUMS` must agree with all four records. Archives contain exactly one ordinary member named `ghtui`; licenses/source provenance are separate release assets. Archive members are never extracted by pathname: only that verified member is streamed into a private named staging file. Archive/payload declarations are capped at128MiB; resource-limited extraction has an independently conservative at-most256MiB temporary-file ceiling across Bash platform units, followed by exact size/digest validation. Metadata/listing/capture are separately bounded.

An owned0600 receipt records a current digest plus, while transitioning, one pending digest. It is atomically written BEFORE the final same-filesystem binary rename. That rename is the commit boundary and last required fallible install effect; no second required metadata write can convert a committed usable binary into a reported install failure. A later invocation resolves the receipt only from the actual exact old/new digest. A third digest refuses all overwrite/uninstall. A mkdir lock serializes installers; a stale/unknown lock blocks rather than guessing process identity or automatically removing it. Recovery guidance requires explicit inspection and removal of only that known lock after confirming no installer remains. Configuration/cache/drafts/repos and shell profiles are not uninstall targets.

Linux admission additionally checks a bounded ELF64 program table with no PT_INTERP; macOS checks an actual thin64 executable CPU header. These checks do not establish Rust target provenance, musl implementation, minimum OS/CPU/runtime compatibility, signing or notarization. The known `ghtui --version` branch is child-free; bounded CPU/output/wall validation cleans only the install shell's actual owned job. This is not a sandbox for compromised publisher code or arbitrary descendant-containment proof. Bash/system tools and the publisher remain trust boundaries.

The developer-only Node release assembler accepts already built matching-host binaries and records exact source-tree/binary/archive hashes; it never builds Rust or publishes. Installer users need no Node/Rust/jq. Product PTY declarations require explicit `GHTUI_RELEASE_TEST_FIRST` and `GHTUI_RELEASE_TEST_SECOND` metadata inputs for two genuinely separately versioned QA archives. Root will prepare actual Cargo package-version builds under serialized limits (static musl target on Linux), recording source/build/hash provenance. Missing/inconsistent inputs fail clearly; no skipped test, relabeled same binary, installed wrapper, implicit build, development-binary launch fallback or public-release assumption is allowed. Native macOS/four-target/release-profile/hosted publication evidence remains separately required.
